# V1 架构决策记录

日期为 2026-11-19，Asia/Shanghai。**ERPNext v16 + 独立 HaxpowerPlatform Frappe App 已获项目方原则批准，作为 V1 首选技术路线。** 正式实施仍需通过审计、权限、备份恢复及库存验收。
[项目决策记录](DECISIONS.md) · [Stage 2B 验证](STAGE2B-LIGHTWEIGHT-AUDIT-REPORT.md)

## 背景与理由

- 复用 ERPNext 原生库存单据、批次分配、流水、余额和在途接收，减少自建库存引擎及其长期维护责任。
- 未来可能引入库存价值、采购及销售，具备复用原生能力的空间。V1 范围仍以数量为主。
- 员工通过 Haxpower 自定义界面和受控 API 办理库存业务。独立 App 负责领域模型、仓库授权、流程、纠错及对外语义。通过 Hooks 和受支持接口集成，保留核心源码原样。
- Stage 2A 的 Frappe-only 已在隔离站点通过同类收发、事务、盘点和权限测试，保留为经验证的备选。它在真实 NULL 和领域账本上有优势，须由项目长期维护库存引擎。
[Stage 2A 对照](TECHNICAL-ROUTE-COMPARISON.md) · [适配边界](ERPNEXT-V1-ADAPTATION-BOUNDARIES.md)

## 审计实施建议

建议以 Stage 2B 验证的方案 A 为 V1 审计基线。ERPNext 有效 SLE 与已提交 Bundle 提供数量事实，Bin 是原生仓位汇总。独立 App 持久保存每笔受控操作的操作者、时间和请求身份，以及纠错原因、原单原行和更正单关联。历史错误用同一事务内的新原生单据与新日志更正。

Stage 1F 的完整业务事件方案保留为审计备选。当业务要求独立留存历史批次和数量、在原生账损坏时复核原始事实，或试运行发现方案 A 无法可靠隔离写入口时，应重新评估。数据库管理员不可篡改、法定留存或外部可验证等要求需要独立控制，单靠应用内任一方案无法满足。
[追加式业务事件验证](STAGE1F-AUDIT-COUNT-REPORT.md)

## 正式实施门槛

| 条件 | 评审要求 |
| --- | --- |
| 审计 | 复核轻量日志覆盖所有受控库存写入，验收同事务、请求唯一、原单行关联及日常查询。审批、附件与需要独立证明的原始事实须明确记录及保留要求。 |
| 权限与高权限操作 | 员工业务账号执行服务端角色和仓库范围检查。限制原生库存读写、取消、导入/导出和可泄露批次数据的入口。验证所有启用的原生单据和后台路径，梳理管理员、服务账号与计划任务。 |
| 备份恢复 | 在隔离恢复环境验证同一恢复点的单据、SLE、Bundle、Batch、Bin、日志、权限及私有附件。复核在途、幂等、未完成盘点与重估队列。 |
| 库存 | 两段/部分接收、精确批次、负库存、精度、并发及异常回滚保持既有门槛。补齐动态仓库、期初导入、按桶盘点截止、依赖下游的纠错和其他未验收场景。 |
| 版本 | 对本轮 Frappe/ERPNext 16.55.0 的结论建立升级回归。Batch、Bundle、SLE、保留映射、重估、过账时间和关闭期间均需复核。 |

本记录确认架构方向。盘点冻结或版本规则、批次大小写与清洗处置、同仓不同库位的移库、下游补偿、审批及留存要求仍由业务审查决定。Stage 2A 的相反推荐保留为当时的技术对照结论。
