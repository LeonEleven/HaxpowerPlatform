# 库存模型设计

## 1. 核心原则

库存按以下维度管理：

**Stock Item（SKU） + Warehouse + Location + Batch（可空） + Quantity**

批次是库存维度，不是产品档案中的单一字段。

## 2. 批次规则（已确认）

- 批次号为自由文本，不要求固定格式。
- 入库允许无批次库存。草稿可暂未选择批次，正式提交须指定实批次或明确无批次。
- 同一 SKU 下相同批次号复用同一 Batch 记录。
- 不同 SKU 可以使用相同批次文本。
- 当前不考虑同一 SKU 的同一批次号重复使用代表不同实物批次。
- 有库存流水的批次不可删除。
- 同一 SKU 可以同时存在有批次和无批次库存。
- 领域模型中 `batch_id = NULL` 表示无批次，不创建普通假批次。
- ERPNext 若需要特殊 Batch 映射，只能存在于适配层，不能污染领域模型。

批次文本的等价规则、长度、历史例外和归并签核仍由 B03 确认。V1-06 在合成站点验证版本化候选规则。

## 3. 有批次、无批次、未选择批次

示例：

| SKU  | 仓库   | 库位     | Batch          | 数量 |
|------|--------|----------|----------------|-----:|
| 6003 | 上海办 | 正式库区 | STD61          |   12 |
| 6003 | 上海办 | 正式库区 | STD62          |   20 |
| 6003 | 上海办 | 正式库区 | NULL（无批次） |   15 |
| 6003 | 上海办 | 瑕疵库区 | NULL（无批次） |   12 |

- 实批次使用 `{"mode":"BATCH","batchNo":"STD61"}`。批次身份按 SKU 隔离，显示保留经确认的原文。
- 明确无批次使用 `{"mode":"NO_BATCH"}`。业务响应中的 `batch` 为 `null`。
- 缺少选择或模式表示未选择。提交须提供有效选择，空值、空白和疑似空引号会进入校验错误。

V1-06 在 `HP V1 Batch Mapping` 保存稳定映射 ID、SKU、种类、原文、规范键、策略版本、状态、创建身份和创建时间。每个 SKU 有自己的无批次系统桶。不同 SKU 可独立使用相同批次文本。ERPNext Batch 标识只在受控适配和管理员诊断中解析，库存模型继续以可空领域批次维度表达无批次。

[API 批次契约](API-CONTRACTS.md#4-批次字段约定) · [候选规则和原生 Batch](ERPNEXT-V1-ADAPTATION-BOUNDARIES.md#批次输入规范)

## 4. 仓库与库位

- 领域仓库可动态新增，每仓可建多个库位。V1 无需货架或货格层级。仓库和库位各有稳定 ID，库位编码在所属仓库内唯一。
- 每个域库位独占一个 ERPNext 原生叶仓。领域仓库记录公司和一个显式选择的同公司顶层 ERPNext 分组仓。多个领域仓库可引用同一个原生分组仓，各自的 ERPNext 叶仓直接挂在该分组下。所有库存维度以领域库位 ID 表示。
- V1-04 支持维护显示名称和描述。停用先检查已知库存和引用，待 V1 库存流程能够完整验证未结单据并协调并发库存写入后再开放。保留已建仓库、库位及原生映射身份。
- 普通库位选择要求仓库、库位及原生映射有效。V1-05 在领域仓库 ID 上接入员工操作权限和数据范围。仓库及库位正式编码、维护职责和授权矩阵仍属 B02。

## 5. StockBalances 当前库存余额

以下为逻辑读模型。ERPNext V1 从原生单据、有效 SLE、已提交 Bundle 与 Bin 读取和核对数量，App 只保存业务单据和操作引用。

逻辑唯一键：

`stock_item_id + warehouse_location_id + batch_id`

字段建议： - `id` - `stock_item_id` - `warehouse_location_id` -
`batch_id`（nullable） - `quantity_on_hand`（Decimal） - `updated_at` -
`row_version`（并发控制，可选）

同一维度只能有一条余额。数据库必须处理 NULL
唯一性：有批次记录和无批次记录分别建立唯一约束/索引。

## 6. StockLedger 库存流水

库存流水是库存变动审计事实，正式写入后不可直接修改或删除。

字段建议： - `id`, `transaction_id` - `document_type`, `document_id`,
`document_line_id` - `stock_item_id`, `warehouse_location_id` -
`batch_id`（nullable） - `quantity_delta` - `transaction_type` -
`operator_id` - `occurred_at`, `created_at` - `remark` -
`reversal_of_ledger_id`（可空）

移库可形成多条流水：源库位减少、在途增加、在途减少、目标库位增加。余额更新和流水写入必须同一事务完成。

## 7. 在途库存

移库发出后，货物离开源仓库但未被目标仓库接收，应计入在途库存。

V1-04 以独立的系统在途领域仓库及库位预留该维度，并创建同公司的 ERPNext `warehouse_type = Transit` 叶仓。在途位置继承系统仓库类型，从普通仓库、库位和原生领料选择中排除。系统位置由站点运营人员通过内部服务配置。V1-10 接入发出和归属对账。V1-11 支持逐行部分接收、多次接收及剩余在途返源。

可以使用受系统保护的 Transit Warehouse/Location 或专门在途余额模型： -
纳入公司库存总量。 - 不纳入普通仓库可用库存。 -
普通员工不能将其当作普通仓库直接出库。 - 保留
SKU、批次、数量和原移库单关联。

部分接收时，按实收数量转入目标库位，剩余继续在途。

## 8. 禁止负库存

- 禁止负库存。
- 草稿可暂存超过库存的数量。
- 正式提交时服务端重新校验。
- 并发扣减必须安全。
- 批次库存不足不能自动从其他批次补足。
- 无批次库存不足不能自动从有批次库存扣减。

## 9. 单位与精度

- 产品数量通常是整数，其他单位可能有小数。
- 使用 Decimal/Numeric，不使用 float/double 存储库存数量。
- 每个 SKU 绑定库存单位及精度。
- PC=0、KG=3、M=3 仅为示例，实际精度可配置。
- 不允许超过单位精度的数量提交。

V1-07 按 SKU 的库存单位和精度验证十进制字符串，并按命令检查正数、零或有符号非零数量。单行上限由调用方显式提供。规范表示去除无意义的末尾零并无损往返数据库，合成参数仅用于测试。

合计按 `Company + SKU ID + Location ID + Domain Batch Identity`，源与目标分别计算。无批次占独立的 `NO_BATCH` 桶，真实批次按领域映射 ID 隔离。多行可以共享同一个桶，合计后仍保留所有原行和行序。V1-08/V1-09 接入真实收发及可用量判断。

## 10. 盘点

按
SKU、库位、批次（含无批次）分别记录账面数量、实盘数量、差异、盘点人、时间和备注。差异通过正式调整流水生效。

B05 于 2026-11-25 经项目负责人批准：盘点不冻结库存，支持 LOCATION / SKU / BUCKET；以库存版本判定过期，不设固定时限。旧任务保留并另建快照、重新确认实盘。允许授权发现原账面零的新桶。见 [正式决策及来源](DECISIONS.md#8-b05-正式盘点规则2026-11-25)。B06 审批与 B12 记账截止仍待确认。

## 11. 库存估值扩展

V1 不启用金额、成本和利润。未来可增加独立的
InventoryValuationLayer、InventoryCostEntry、StockValuationAdjustment。数量流水与估值流水分离。

采用 ERPNext
时必须验证其内置估值行为，即使业务界面不展示金额，底层也可能仍维护估值数据。

## 12. V1-08 多行入库

入库草稿保留稳定单据 ID、逐行业务 ID、目标库位、库存单位、Decimal 数量字符串和显式批次选择。提交重新核对当前仓库授权、同公司物理叶仓和 SKU/Item 映射，然后在共用库存锁内解析或首次创建 Batch 映射。系统在途不能用作入库目标。

ERPNext 为每条业务行生成一条 Stock Entry Detail、一个已提交的入向 Bundle 和一条有效 SLE。即使两行是同一库存桶，原生明细也分别保留。无批次使用该 SKU 的独立系统 Batch，业务结果仍为 `NO_BATCH`。入库在提交前核对受影响 Item/叶仓的有效 SLE 与 Bundle 分配、Batch 总量和 Bin 汇总。操作日志把业务行连到原生明细。

正式员工写入等待 B01、B03 与 B12 确认。V1-09 可复用执行内核和原生数量核对思路，并增加指定批次的可用量、扣减校验与出向 Bundle 适配。

## 13. V1-09 多行出库与可用量

出库草稿固定每行的 SKU、源库位、批次选择及库存 UOM。真实批次使用已有领域 Batch ID。明确的无批次库存使用 `NO_BATCH`，领域 Batch ID 为空。适配层将该选择映射到 SKU 专属系统 Batch。提交重新核对映射和每个源仓的员工授权。

可用量是已提交的物理数量，按公司、SKU、物理叶库位和领域批次计算。适配层以有效 SLE 和对应已提交 Bundle 的带符号数量为事实，核对逐桶汇总、原生 Batch 总量和 Bin 的 SKU 库位汇总。缺失关联、映射漂移、小数精度不符或余额不一致会阻断出库。B09 库存预留待确认。

同桶各行先合计需求。持有共用库存写入锁后重新读取源桶，每个桶独立判断库存是否充足。ERPNext Material Issue 将业务行对应到负向 SLE 和 Outward Bundle。指定桶刚好扣完时仍可核对到零。未选中的真实批次、无批次、品牌 SKU 和库位数量须保持原值。

## 14. V1-10 移库发出与在途归属

移库草稿固定每行的 SKU、源库位、目标库位、显式批次、库存 UOM 和 Decimal 数量。发出时，两侧物理库位都须属于业务单的 Company 并映射到已验证的原生叶仓。员工须有 Transfer 权限及两个仓库范围。每个合成 Company 使用一个经核验的系统 Transit 叶仓。

每条领域行各有一个原生发出 Detail 和一条独立的在途归属。该 Detail 对应源叶仓的负向有效 SLE 与 Outward Bundle，以及 Transit 叶仓的正向有效 SLE 与 Inward Bundle。两侧数量、Item 和批次相同，符号相反。ERPNext 不向该行的目标物理库位记账。若同一单据的另一行把该位置用作源库位，该位置只按源行扣减。

共享在途仓可能汇总为 30 件。发出 10 件和 20 件的两条原始行分别拥有自己的 10 件和 20 件额度，各自关联其原生入向 SLE。归属仅保存引用，已发数量取自固化行并与原生事实核对。存在孤立在途流水、失效引用或归属合计差异时，相关 SKU 的发出和已发详情读取消失败。

### V1-11 逐原行接收与退回

原发出行以 `已发 = 累计实收 + 累计已退 + 剩余在途` 守恒。每次接收或返源的关联对应
同一原行归属及后续原生 Detail，通过两侧 Bundle 和有效 SLE 核对精确数量。相同公司、SKU、
在途叶仓、批次的各原行剩余量合计等于原生桶库存，同时校验每条原生流水及其归属。
原生累计实收必须等于该原行已接收量。ERPNext 原发出量减原生实收等于领域在途加累计已退。
缺少归属、孤立流水、Bundle 缺失、重复关联或累计差异会阻止数量操作。已关闭原行继续参与历史核对。
同仓不同库位仍待 B04 审定。

### V1-12 版本与盘点数量

三级库存版本属于明确 generation，按真实有效数量动作单调推进；库存 8→6→8 仍使旧任务过期。LOCATION 覆盖库位全部 SKU/桶，SKU 覆盖该库位指定 SKU 全批次，BUCKET 仅覆盖明确桶。其他范围的合法数量变化不使指定范围错误过期。无差异完成不推进数量版本；版本不是余额或第二本数量账。

账面快照只由服务端生成。实盘 NULL 为未确认，0 为显式确认没有库存；所有快照行必须确认，不遗漏自动盘亏。差异为 actual−snapshot，各批次独立处理。新增发现桶须证明原截止账面为零；无法证明时重盘。任务无固定有效时限，版本不连续或范围改变时另建任务重新确认。系统 Transit 仍由 V1-11 在途归属对账负责。
