# 技术架构设计

## 1. 架构目标

- 满足当前约 11 名用户、1000 种以内 SKU。
- 低复杂度、易维护、性能稳定。
- 阿里云 Linux 部署，互联网浏览器访问。
- 为微信小程序、AI/OCR 和外部系统预留 API。
- 核心业务模型尽量不绑定 ERPNext 内部结构。
- 不过早采用微服务。

## 2. 架构风格

V1 建议采用 API-first
模块化单体，而不是微服务。当前规模不需要先引入分布式部署、消息总线或服务网格。

模块建议： - Identity & Access - Product Catalog - Warehouse -
Inventory - Stock Documents - Approval - Search - Audit - Integration -
Future AI Document Processing

## 3. 分层

``` mermaid
flowchart TB
    WEB[桌面网页] --> API[Haxpower API]
    MINI[未来微信小程序] --> API
    AI[未来 OCR / AI 服务] --> API
    API --> APP[应用服务层]
    APP --> DOMAIN[领域模型与业务规则]
    DOMAIN --> PORTS[库存引擎适配接口]
    PORTS --> ERP[ERPNext Adapter / 自研库存引擎]
    ERP --> DB[(数据库)]
    APP --> JOBS[后台任务队列]
    JOBS --> OCR[OCR / AI 外部服务]
```

前端只调用 API。库存服务负责业务校验和事务，不允许前端直接写数据库。

## 4. 技术路线

### A. V1 实施基线 · ERPNext v16 + HaxpowerPlatform Frappe App

- 复用 ERPNext Item、Warehouse、Batch、Stock Entry、Stock Ledger
  等能力。
- 自己实现产品规格层、专属界面、API facade、审批开关和业务定制。
- 不修改 ERPNext 核心源码。
- 风险：同一 SKU 混合有批次/无批次、估值机制、报表权限和自定义库存流程。

### B. Frappe Framework + 自研库存引擎

- 复用 Frappe 用户、角色、DocType、API、文件和后台任务。
- 不依赖 ERPNext 库存模型。
- 需自行实现库存流水、余额、批次、在途、盘点、并发和一致性。

### C. 独立技术栈

- 可评估 Vue 3 + TypeScript、ASP.NET Core、PostgreSQL 等组合。
- 产品、库存、权限、审批、API、文件、任务和审计全部自研。
- 自主性最高，但初期工作量最大。
- 此组合只是候选，不是已经决定的技术栈。

### V1-02 规格维护与事务

- `haxpower_v1.catalog.service` 提供以领域 DTO 为输入和输出的内部 Python 服务。调用方使用已认证的 Frappe 会话，工程角色 `HP V1 Catalog Maintainer` 须显式授予。内建 Administrator 可在受控服务器环境调用。普通员工无档案服务访问权。DocType 的 `System Manager` 权限仅用于读取诊断数据，常规 DocType 保存、删除及改名经过控制器防护。
- 规格主记录和属性子表由 Frappe 在同一事务写入。维护服务先锁规格 DocType 元数据行，之后读取最新配置和规格版本。该站点级锁串行化目录写入。规格更新核对调用方传入的版本，属性变化与审计写入使用同一保存点。调用方负责外层提交，任一审计写入失败回滚本次编辑和已写审计。
- 单列编码唯一约束来自 DocType `unique` 元数据。选项和模板的复合唯一约束由安装及迁移末尾的幂等钩子创建并核对列序，复跑保留已有数据。选项和模板采用独立 DocType，可按所属属性或分类查询。规格值作为子表，读取不依赖最新模板。Decimal 值保留原有精度，跨规格数值范围搜索需要 V1-15 定义查询表示。
- 审计保留明确编辑的前后值、操作者、时间、规格版本和操作 ID。记录只允许服务新增。数据库维护、备份恢复和受信任的服务器代码继续遵守运维控制。V1-05 结合 B02 复测角色及已启用入口后再对员工开放。
- V1-03 可以通过 `get_specification(specification_id)` 获取稳定 ID、分类、状态、版本和类型化属性。调用者用规范的规格 ID 关联 SKU，按其自身业务入口授权策略校验。未来公开接口由外层将 DTO 转为契约表示。

### V1-03 SKU 与原生主数据

- `catalog.sku` 是内部 Python 服务，复用目录维护授权、事务保存点和规格读取契约。目录写仍按站点串行化，写入期间以当前读校验规格、品牌及映射。品牌编码、SKU 编码和 SKU 的 Item 链接各有数据库唯一约束，独立连接竞争时只有一个事务成功。
- `adapters.erpnext.item` 使用原生 `Item`、`UOM` 和叶子 `Item Group`。新 Item 初始编码取规范化 SKU 编码；显式关联可使用名称独立的既有 Item，须通过身份、单位、状态和已知库存引用检查。适配器复核原生列和单位换算行，原生库存 UOM 的换算因子固定为 1。创建和关联均使用原生 Document 保存，无期初数量、估值、价格及台账写入。
- 领域 SKU 保存唯一的原生链接、库存 UOM 和 Item Group。Item 用 App 安装的 Custom Field 保存反向领域 ID。内部领域查询只返回映射状态；站点 Administrator 可按 Item 名称复核孤立标记、重复标记、缺失 Item 或原生字段漂移。适配器和领域记录使用同一事务。外层调用方负责提交，服务保存点撤销失败操作中的 Item、SKU 和子表。
- 受管 Item 通过文档钩子保护标记、编码、显示名、组、状态、库存单位、换算和跟踪方式，并拒绝删除、重命名及合并。被 SKU 引用的 UOM 和 Item Group 受对应身份和语义保护。普通 ERPNext Item 维护继续由原生权限处理。数据库管理员、任意受信任服务器代码和元数据维护由运维控制约束，映射诊断用于复核绕过文档生命周期的漂移。
- V1-05 建立员工能力、原生入口守卫及仓库范围。B02 的正式档案字段授权待确认。V1-06 通过受控适配接入批次能力及逐 SKU 的系统批次。V1-07/V1-09 负责库存引用、检测与写入协调，随后复核停用条件。B01 生产单位、数量精度和上限经确认后在原生流程中完成 Decimal 往返和边界验收。

[开发配置和演练](../dev/v1/README.md#品牌与-sku-内部维护) · [产品模型](PRODUCT-MODEL.md#13-v1-03-品牌库存-sku-和-item-映射)

### V1-04 仓库、库位与原生叶仓

- `haxpower_v1.warehouse.service` 提供内部维护、稳定 ID 读写和物理库位校验。站点管理员显式授予工程角色 `HP V1 Warehouse Maintainer`。领域 DocType 的常规 CRUD 由控制器阻断。原生权限及查询钩子隔离受管叶仓，DocShare 守卫阻止原生共享授予，未受管原生仓库仍遵循 ERPNext 权限。
- 原生适配器接收明示的同公司顶层分组仓，使用 ERPNext Document 接口创建叶仓或显式关联同组、同公司、已启用且无已知引用的现有物理叶仓。新建叶仓采用 `HPV1-<location_id>` 作为 `warehouse_name`，由 ERPNext 按 Company 简称生成原生名称。领域 DTO 使用稳定领域 ID，维护诊断单独核对正向链接、反向标记、公司、状态、原生树和原生仓库类型。
- 领域写入用站点级数据库行锁串行化维护操作，在保存点内锁定公司、分组仓或现有叶仓并使用当前读，数据库唯一键约束仓库编码、局部库位编码和原生叶仓占用。叶仓创建、反向标记和库位记录同事务提交。常规原生改名、合并、树身份变更、删除及领域重映射受到保护。
- V1-04 只开放显示名称和描述编辑，要求 `expected_revision`。停用检查 Bin、原生流水、子仓及已知原生单据引用，再默认拒绝，等到 V1-07 至 V1-11 完整引用和记账写入协调接通。系统在途由站点运营人员独立配置，原生 Stock Entry 和 SLE 路径拒绝使用该位置，V1-10/V1-11 接入受控移库。
- V1-05 在 `warehouse_id` 上执行操作权限和仓库范围校验，并在获取库位、报表及导出前应用服务端过滤。B02 的编码、实际维护岗位、ALL/SELECTED/NONE、默认矩阵及导出范围待确认。

### V1-05 员工授权与受控适配

- `access.policy` 以当前会话用户、启用技术角色和公司内稳定仓库 ID 校验访问。
  仓库范围读取及角色读取均进入当前请求事务，下一次请求使用更新后的权限。
  未知、失效、未授权及系统在途库位共享同一拒绝结果。
- `access.api` 返回最小业务投影。搜索及分页按已授权仓库和有效物理库位计算，
  现有内部服务负责诊断映射及维护受限字段。未来库存查询、报表和导出复用仓库授权规则。
- `access.execution` 使用以当前用户、服务、指定原生记录、领域 ID 和生命周期阶段
  为范围的内部上下文。适配层校验维护权限后，以同一用户在服务保存点内写入原生文档。
  Frappe 记录仍归因于该用户，退出和异常恢复上下文及请求配置。
- `access.request` 在认证之后、路由分派之前限制原生 HTTP 请求。
  已登记的原生库存维护计划保持停止，worker 在执行前检查队列方法及 DocType。
  路由、ORM 和后台守卫范围及后续启用条件见
  [原生入口矩阵](ERPNEXT-V1-ADAPTATION-BOUNDARIES.md#v1-05-原生入口矩阵)。
  V1-06 在 Batch 识别扩展点接入持久映射，受控批次和库存写入各自具有范围与执行授权。

### V1-06 批次映射和事务

- `inventory.batch.normalization.normalize_selection` 验证三态并返回类型化选择。实批次规则保留原文、候选值及版本。ASCII 十六进制键按 Unicode 码点定长编码，MariaDB 的大小写或重音排序规则不会丢失字符差异。无批次用固定非空哨兵。表约束保证身份键非空、系统桶唯一及原生 Batch 一对一。
- `inventory.batch.service` 提供 `preview_selection`、`resolve_or_create`、`resolve_existing` 和 `get_batch`。通过 SKU 行锁和当前读取协调并发创建。Item 启用、原生 Batch 插入和领域映射在调用方事务及同一保存点中，服务返回稳定 ID 和是否新建。失败回滚到保存点，调用方负责提交或重试。
- ERPNext 适配器从稳定映射 ID 解析原生 Batch，验证两个方向、启用状态及修订漂移。`resolve_native_batch` 在事务内重新验证和锁定，`diagnose_mappings` 是站点管理员的 Bench 诊断。Batch 创建复用 V1-05 的当前身份执行上下文，并绑定 SKU、映射和原生记录。创建以外的原生生命周期仍受库存守卫保护。
- V1-07 在共用事务入口接入仓库和操作授权并管理锁及重试。V1-08 入库复用预览与创建接口。V1-09 出库按已选领域身份或明确库存桶查找既有映射，并在原生记账前复核。同一单据多桶的锁顺序在 V1-07 验证。B03 确认及业务授权接入前，候选写入限明确配置的隔离站点、合成 SKU 和 Bench 管理员。

## 6. 库存事务

正式库存提交应在一个事务中： 1. 校验用户权限。 2. 校验单据状态。 3. 校验
SKU、仓库、库位、批次和单位。 4. 校验可用数量。 5.
并发保护并扣减/增加库存。 6. 写入不可变库存流水。 7. 更新库存余额。 8.
更新单据状态。 9. 提交事务。

任何一步失败，整体回滚。

1000，可先用数据库索引和查询优化，不必立即部署独立搜索集群。搜索字段包括

## V1-07 库存执行内核

`inventory.operations` 使用独立的 MariaDB 主库连接。一次调用在一个事务下完成，保留已认证的 Frappe 会话身份。锁顺序为站点库存写入守卫、Company、请求、业务单头及稳定 ID 排序的单行、仓库范围和按稳定 ID 排序的库位与仓库、SKU、批次映射，再执行原生步骤并写操作日志、状态和请求结果。认证主体和操作角色会在进入请求处理前锁定读取，仓库范围按持久化单据重新授权。站点守卫同时覆盖 V1-06 的 Batch 首次创建，因为多个公司可使用同一 SKU。无批次且暂无映射时仍在守卫下处理桶身份。关键数据用 `FOR UPDATE` 从最新提交版本读取。

内部适配契约为 `Action` 和 `Plan`。动作绑定操作能力、数量符号语义、单位上限和原生引用验证；执行计划包含稳定行与源、目标各自合计。逻辑数量使用 Decimal，业务持久化使用可精确往返的十进制字符串。合成执行写两个父单和独立的明细 ID，返回 `NativeLink`。内核逐条核验父子归属、动作约束及业务行覆盖。原生动作、日志头、原生关联、状态和请求结果一起提交。执行阶段拒绝内部事务控制、DDL、自动提交和 Frappe 事务回调。合成写入不经过会通知或入队的 ORM 生命周期。

事务失败关闭独立连接，由 MariaDB 完整回滚；死锁和锁等待超时重试使用同一请求键重新走授权、锁和校验。提交结果未知时，关闭原连接后在新连接取得相同守卫并核对已提交状态，核对路径不写入。确认已有结果就重放，确认请求缺失后才允许同键重试。无法确认时保留提交不明状态。请求保留和日志生命周期待 B08 签定。

V1-08 的入库动作需把 API DTO 解析成领域单据和稳定行，由当前用户权限进入受控原生适配器，适配器确认批准的批次策略并校验实际提交的原生明细及 Bundle。入库如需首次创建批次，应在执行内核的外层事务与共用守卫下接入，保留原生 Batch 和领域映射的原子性。V1-09 复用同桶合计来检查可用量。V1-10/V1-11 以各次发出、接收或退回的稳定动作身份及原行剩余量扩展生效约束。V1-12 增加锁定盘点任务、截止和原生账核对。V1-14 在同事务锁定并授权原操作和原行业务额度，记录新旧原生引用。上述动作各自定义状态迁移和生效唯一性，审批策略由 V1-13 接入。

## V1-08 多行 Material Receipt

入库复用 V1-07 的当前读、请求摘要、站点库存写入锁、事务及恢复。草稿保存显式选择。提交在该事务中调用 V1-06 的批次解析与首次映射逻辑，逐行生成 ERPNext Material Receipt 原生明细。Action 使用 RECEIVE 能力与独立的目标仓库授权。候选估值设置随显式 Bench 上下文传入，HTTP 和正式员工写入仍关闭。

原生写入上下文绑定当前员工、领域单据、Company、原生 Stock Entry 实例及逐行核准的 Item、Warehouse、Batch 和数量。ERPNext 把明确指定的行批次转换为入向 Bundle，并在 SLE 提交链中提交 Bundle。适配器在同一事务核对原生明细、Bundle、有效 SLE、Batch 和 Bin，随后由执行内核记录操作及行链接。既有 V1-07 请求摘要继续使用原格式。

V1-09 可复用共用事务内的权限、行关联、批次解析和库存核对原则。出库需对合计后的指定桶做可用量当前读，并实现独立的出向上下文与原生校验。

## V1-09 多行 Material Issue

`inventory.issue.service` 在共用库存事务中校验 ISSUE 权限、源仓范围、SKU、物理库位和已有批次映射。V1-07 `Plan.source_demand` 使用 Decimal 合计相同桶的行。库存 guard 后以锁定读取核对 SLE、Bundle、Batch 和 Bin。Material Issue 事务使用 MariaDB READ COMMITTED，使 ERPNext 的普通查询在等待锁后同时取得最新的已提交数量和估值。

`adapters.erpnext.issue` 用 ERPNext 原生 Stock Entry 创建和提交 Material Issue。每行绑定精确的批次和源叶仓。两种 Stock Entry 动作共享出入方向校验、原生作用域与逐行对账，继续使用 V1-08 的缓存、回调、队列与即时消息保护。数量、会计和业务事实在同一事务内提交，断连按原幂等键恢复结果。

V1-10 可复用 `Plan.source_demand`、源桶核对和 Outward Bundle 的符号、批次和明细校验。源目标双权限、在途归属和两阶段状态由移库任务接入。B01 数量参数、B03 批次规范、B08 日志保留、B09 预留与 B12 估值和维护上线条件均待确认。

## V1-10 两阶段移库发出

`inventory.transfer` 使用 V1-07 命令事务及同一幂等请求表。事务取站点库存写入守卫及公司锁，按稳定 ID 读取业务行及物理映射，重验 Transfer 能力与源和目标仓库授权。合成写入使用 READ COMMITTED。适配器解析同公司的唯一有效系统 Transit 位置，使用 V1-09 的源桶合计与原生数量核对。B04 未批准时，常规发出路径拒绝同仓不同库位。隔离合成环境可显式启用技术验证。

同一公司共用一个系统 Transit 叶仓时，原生数量可汇总，业务履约按原行归属。适配器在原生过账前复核受影响 SKU 的在途流水与已持久化归属，随后为每条原始行验证同一原生 Detail 的两条 SLE 与两个 Bundle。操作日志、原生关联、在途状态和逐行归属共用同一提交。提交结果未知时沿用独立新连接恢复请求。

V1-11 可在当前写事务调用 `lock_original_dispatch`，持有相同库存守卫并取得原发出身份和已发数量，使用原发出 Stock Entry 作为 `outgoing_stock_entry`，并以 Detail ID 作为 `ste_detail`。后续接收或退回在共同库存写入守卫内锁定原归属，确认固定库位、SKU、批次和剩余量，按原行追加有效动作。V1-11 须把在途核对扩展为已发、已收及已退三类有效动作的净量核对。

## V1-11 部分接收和剩余返源

接收与退回共用库存执行内核。组织库存写入守卫、请求行、业务单及原行、权限和映射、
原生入账、日志与状态更新都位于同一提交边界。接收、退回以及并发重试竞争相同的逐原行
余量。历史请求先验证当前身份与原单两侧授权，再用已提交请求及操作日志返回原结果状态和
revision。追加动作推进业务单 revision，保留原发出操作引用。对账从原发出累计接收和
返源事实推导余量，并以原生有效 SLE、Batch Bundle、Bin、Batch 合计及历史摘要验证。

V1-12 的共同集成点是 `inventory.operations.service._stage` 的受控写入事务。V1-11 的
私有 `Plan.source_demand` 和 `Plan.target_demand` 按公司、SKU、领域库位、批次种类及
可空领域批次 ID 表达影响桶。入库影响目标，出库影响源，发出影响物理源及系统 Transit
（原生适配从目标计划之外补出实际在途腿），接收影响系统 Transit 和原目标，返源影响
系统 Transit 和原源。V1-12 应从已核验的实际双腿统一提取桶及库位版本推进集合。

### V1-12 非冻结盘点及统一数量版本

B05-01–04 于 2026-11-25 经项目负责人批准，来源见 DECISIONS 第 8 节。单个物理库位支持 LOCATION / SKU / BUCKET。服务端在共享库存写守卫内生成快照和独立代次、范围/桶计数器。LOCATION/SKU 包括有效历史中的归零桶，BUCKET 可显式选择合法零桶。每行须明确确认；未填写和实盘零分别持久化。发现行只有在包围范围未变、桶无原生历史且版本连续时才证明原账面零，批次建档复用 V1-06 的受控入口。重盘追加任务并保留原任务和实盘，不复用旧实际值。

统一 `_stage` 在原生执行前核对版本基线，执行后从已核验 Native Link 的真实 SLE/Bundle 提取所有数量动作，再在同一事务推进三级计数器。移库以实际源/Transit/目标腿提取，避免把计划目标误计为发出时已收货。计数器为精确整数文本，NO_BATCH 使用非空独立键；零余额仍保留版本。无差异 Count 专用预期关联集合为空，日志明确 quantity_effect=None；既有命令仍要求所有业务行有原生关联。

版本的事实摘要仅用于诊断越界数量或原生身份变化，忽略 modified 和纯估值技术字段；它不替代独立持久计数器。每次对账使用当前读，先验证有效 SLE、Bundle、Batch、Bin 与唯一轻量日志归属。发现不连续时停写。当前使用站点共享守卫和全量受管历史核对，便于审查；大数据量时须测量锁持有时间，再在另行证明完整性的前提下优化。

安装/迁移先完成 DDL，再在守卫内对账并原子初始化代次和历史桶/范围基线。重复迁移只验证，保留计数器、任务和历史。初始化失败时没有 Ready 代次，执行内核拒绝数量命令。维护代次切换接口要求独立系统维护能力、事务和守卫；不提供员工 HTTP 入口，B11/B12 的灾后放行政策未决。旧代次任务过期。备份必须对应同一数据库、站点配置及公私文件恢复点。

盘点由 `stock_count.service.complete` 提交确认快照。审批开启时保留待审，批准调用同一盘点校验和执行内核，重验 revision、代次、范围、逐桶版本、实盘完整性及原生事实。已生效错误留待 V1-14 追加反向纠错。


## V1-13 库存审批

锁顺序以站点共享库存守卫开始。提交读取同一锁保护的全局配置，固化当前业务 revision、配置 revision
和仓库范围。待审收发盘点只写工作流，审批关闭则在当前事务记账。移库提交进入待审或待发出，批准
只推进状态。发出在事务内锁定当前提交，核实批准或豁免事件与负载，重新验证源库存及双侧授权。

批准重验审批人和原提交人的授权，使用当前合成运行边界内的原提交人权限执行精确负载。
原生守卫继续绑定原生单据对象、公司和各行。原生落账与数量版本、库存日志、状态、审批事件、
请求结果共享单一事务。原生身份和批准触发者独立保存，无差异盘点没有原生身份及数量动作。

已确认回滚后通过新连接和共享守卫重验提交 ID、状态、revision 和双方授权，追加脱敏失败。
COMMIT 结果未知时使用受同一守卫约束的新连接读原请求结果。没有提交证据且当前读成功时返回
重试要求，连接结果仍未知则保留未知状态。历史重放先授权，过期盘点保留原实盘和失败证据。

`approval.policy.requirement` 提供 V1-14 纠错专项审批与 V1-17 正式期初专项签核的策略标识，
两条未来数量路径仍须各自完成授权、额度或签核证明及验收。

### V1-14 专项审批与审计

V1-14 使用共享库存守卫、不可变专项快照、审批请求和原生关联。专项决定读取当前授权、单据 revision 和快照后，在统一库存事务重算原生数量、原行额度、同桶后续数量动作及已完成盘点。相同时间、无法复核的代次或历史差异进入人工审核。普通路径无法执行纠错动作。混合盘盈盘亏拆分为原生出入库，同一 COMMIT 写入原生数量、日志、版本、请求和审批状态。合成候选采用零估值且拒绝 GL/库存价值差异，生产需 B12 审查。

轻量审计依赖原生有效账和可靠备份，应用文档及 Hooks 约束普通入口。DBA、可信服务和最高权限运维属于信任边界。原生数据损坏时，单靠轻量记录无法独立重建全部历史数量。V1-20 使用多年规模测 shared guard 持锁时间及审批执行身份桥接。

### V1-15 查询一致性及导出

员工查询使用独立 MariaDB REPEATABLE READ、WITH CONSISTENT SNAPSHOT、READ ONLY 连接。权限、目录、版本及原生事实共享快照，读取路径无库存写守卫。公司范围使用已有角色及仓库模型。原生事实验证复用 V1-09/V1-12 并在 Python Decimal 下生成业务净量。V1-15 首版仍按公司复核历史，按请求加载移库和业务历史。快照查询每条 SQL 的上限为 20 秒，
公司历史超过 200,000 条原生流水或单据页涉及超过 100,000 张公司单据时返回容量错误。页面分页、过滤和 Excel 共用服务。权限和数据均实时重新计算，库存响应无共享缓存。

Excel 默认保留 24 小时，可配置 1–168 小时。一站同时一个生成，最多 5000 结果行、10 MiB 文件及 30 秒生成预算。输出列固定，单元格以显式文本写入，Decimal 精确值可以完整往返。导出状态、下载审计和正式业务保留遵循 B08，单独的受控维护命令只清理过期生成文件。反向代理只映射框架公开目录及受控服务端下载入口。生成文件位于 Frappe public/files 和 private/files 路由之外，恢复流程须与数据库一起备份该目录。
