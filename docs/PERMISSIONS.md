# 权限设计

## 1. 总体原则

权限分为两套独立规则： 1. 角色权限：决定用户可以执行什么操作。 2.
仓库数据范围：决定用户可以访问哪些仓库的数据。

访问仓库数据时，两者必须同时满足。API、查询、报表和导出均执行服务端权限检查。

## 2. 多角色

一个员工可以拥有多个角色。操作权限按角色授予集合合并（union）。例如同时有库存查询员和仓库操作员角色，可获得两者授予的操作权限。

仓库数据范围不因多个角色自动扩大，使用独立的用户级配置。

## 3. 初始角色矩阵

项目负责人于 2026-11-27 在 V1-15 任务书第二节批准以下配置基线。应用管理员可以调整组合，实际员工分配另行确认。

| 产品查看 | 是 | 是 | 是 | 是 | 是 |
| 产品维护 | 是 | 否 | 否 | 是 | 否 |
| 参数维护 | 独立授予 | 否 | 否 | 独立授予 | 否 |
| 授权库存与流水查看 | 是 | 是 | 是 | 可选 | 是 |
| 入库、出库 | 是 | 否 | 是 | 否 | 否 |
| 移库、盘点 | 是 | 否 | 是 | 否 | 否 |

## 4. 用户仓库范围

每个用户配置一种模式：

### ALL

可访问授权所属公司的当前可用领域仓库。该公司新增可用仓库后自动纳入。

### SELECTED

只能访问管理员逐个授权的仓库；新仓库默认不授权。授权列表为空时拒绝访问。

### NONE

无权访问任何仓库库存数据。

缺少授权配置时按无仓库访问处理。实际岗位和员工范围经确认后配置。

## 5. 权限计算

查询：`具备对应功能权限 AND 用户仓库范围允许`。

写操作：`具备对应操作权限 AND 源/目标仓库均在授权范围内 AND 业务校验通过`。

移库的发出、接收、退回与全单访问检查源仓和目标仓。V1-10 发出和 V1-11 接收、退回、详情及历史重放复用 V1-05 的双侧校验。B04 的接收职责及同仓跨库位策略待确认。

## 6. 必须受仓库范围保护的资源

库存列表、产品库存详情、批次库存、库存流水、库存单据、在途库存、报表、Excel
导出、API 搜索和详情、与受限单据关联的附件。

不能先查出全部库存再仅在前端过滤；必须在服务端查询和权限层统一约束。

## 7. 产品档案与库存权限分开

员工可能有权查看产品名称和技术规格，但无权查看某些仓库库存数量。产品技术档案查看权限与库存数据范围分开配置。

## 8. 管理员

管理员拥有系统管理权限。管理员账号数量应受控，启用强认证并记录关键操作。管理员
API 密钥不得嵌入浏览器或小程序。

## 9. ERPNext 适配

Frappe 原生支持多角色、DocType 权限、字段权限和 User Permissions： -
https://docs.frappe.io/framework/user/en/basics/users-and-permissions -
https://docs.frappe.io/erpnext/user-permissions

自定义库存
API、报表、导出必须自行验证和补充权限检查，不能只依赖标准表单权限。

## 10. V1-05 技术机制

- `HP V1 Warehouse Access` 按 Frappe User 唯一约束，显式绑定一个 ERPNext Company。
  子表 `HP V1 Warehouse Access Row` 使用稳定领域仓库 ID。配置由 Bench 站点操作员
  调用 `haxpower_v1.access.config.set_scope`。配置没有员工 HTTP 或通用 DocType 入口。
- `access.policy.Operation` 对应 14 个技术角色，覆盖产品查看及维护、仓库查看及维护、
  库存查询、入库、出库、移库、盘点、审批、导出及系统维护。安装时创建技术角色。
  角色合并以启用用户的当前角色记录为准。技术角色的安装不产生员工授权。
- `authorized_warehouse_ids`、`require_warehouse_access`、`require_location_access` 和
  `require_transfer_access` 供业务服务复用。仓库必须是同公司、有效的物理仓，且原生
  父仓可用。库位需要有效的双向叶仓映射。分页总数与搜索只使用授权后的业务记录。
- 员工 `access.api` 只读接口提供仓库、库位、规格和 SKU 的最小标识投影。库位额外包含
  领域仓库 ID。该阶段只开放最小产品投影。V1-15 扩展的授权见本文件末节。
  现有工程主数据维护调用方继续使用各模块的维护权限和内部服务。
- 具备 `HP V1 Transfer` 的用户仍须同时具备源和目标仓权限。B04 确认同仓策略后再开放
  同仓校验分支。V1-05 保存和查询权限配置，库存业务和审批流程由后续任务接入。
- [ERPNext 原生入口矩阵](ERPNEXT-V1-ADAPTATION-BOUNDARIES.md#v1-05-原生入口矩阵)
  记录当前 HTTP 与 ORM 执行边界。运维账号、受控后台与数据库治理由 B11 确认。

### V1-11 接收、退回及历史重放

同一组织的有效身份须具备 Transfer 能力，并能访问原单所有源仓及目标仓。
选择部分原行或重放旧请求也按原单双侧授权，任一侧撤销即拒绝。系统 Transit 叶仓只在
受控动作内解析。普通员工的原生 REST、Desk、End Transit、取消及直接在途写入继续拒绝。
B04 接收岗位及 B07 关闭后补偿仍待项目方确认，合成岗位仅用于隔离验证。

### V1-12 盘点边界

创建、录入、发现、读取、重盘和完成分别在服务器检查 COUNT 能力和该任务物理库位的仓库范围；重放也先重新授权。系统 Transit 不可普通盘点。发现桶验证有效 SKU、批次归属及范围，批次新建复用 V1-06 的受控事务与合成策略。原生 Stock Reconciliation 仅在绑定员工、任务、Item、叶仓、Batch 和精确数量的内部适配作用域中可写；员工 REST/Desk、取消、删除、快照/版本 CRUD 仍关闭。正式员工数量 HTTP 写入保持关闭，B01/B03 工程与验收、B12 正式配置及发布授权仍待落实。


### V1-13 审批

系统配置由 `SYSTEM_MAINTAIN` 控制。提交需要相应业务操作和仓库范围，审批需要
`APPROVE` 与该提交快照的全部仓库范围。审批前重新核验原提交人的业务权限和仓库范围。
有相应权限的创建人可自审。撤回必须由创建人执行并通过当前业务授权；驳回和审批撤销须填写原因。
查看历史和重放需要当前授权。只有审批权限的员工可通过待审提交批准收发或盘点，原生执行沿用该
提交中真实业务操作者的最小权限及精确单据守卫，分别记录批准触发人与原生执行身份。
审批岗位不授予额外的原生权限，B02 正式岗位分配保持待确认。

### V1-14 专项纠错

历史单据的授权申请能力对应 RECEIVE、ISSUE、COUNT 或 TRANSFER。具有 `HP V1 Correction Approve` 与全部相关仓库范围才可专项决定或关闭审核，允许同时满足两项授权的申请人自审。安装和迁移仅创建角色。审批时以当前授权重验提交人与审批人。详情、异常记录和关联查阅也校验仓库范围，关联涉及两个业务单时覆盖两侧。原生执行身份仅在隔离合成环境使用，原生 CRUD 和正式员工数量 HTTP 写入保持关闭。

### V1-15 读取及导出授权

PRODUCT_READ 提供完整业务技术档案和独立目录查询。INVENTORY_READ 要求公司绑定和至少一个授权仓库，随后按合法库位过滤逐桶余额、汇总、流水与 total。仅持有 INVENTORY_READ 时，库存摘要提供 SKU 标识、编码、名称、品牌、库存单位和授权数量。库存关键词匹配及排序也只使用这些基本字段。分类与精确属性筛选需要 PRODUCT_READ。两个读取能力同时有效时，可组合完整 AND 搜索、精确筛选及库存摘要中的规格属性。库存操作角色本身无法调用读 API。完整移库及在途数量遵循两个端点的范围，单侧允许查看自身发生的物理流水腿。普通详情和纠错简要历史仅含业务字段。审批意见、失败和人工纠错审核需在全部仓库授权之上再具备 APPROVE 或 CORRECTION_APPROVE。SYSTEM_MAINTAIN 的原生命令仅用于服务端维护。导出生成、状态和下载检查 EXPORT、对应读取能力、实际覆盖范围及文件所有者。文件记录实际列、需要 PRODUCT_READ 的列，以及筛选或排序是否使用了受限产品字段。撤销 PRODUCT_READ 后，包含技术字段或其筛选结果的文件停止提供状态和下载。只依赖库存读取的文件沿用其库存授权。旧记录缺少可靠字段分类时需重新生成。

## V1-16A 维护授权与 B10 后续设计

服务端通过 `HP V1 Product Maintain` 控制规格、SKU 及 SKU 专属标识和备注，通过 `HP V1 Parameter Maintain` 控制分类、属性、参数选项、模板和品牌。产品维护者可读取录入所需的已有配置。复合规格数据仅接受已存在的选项 ID。两个角色可同时授予，撤权以后续请求的实时授权为准。升级报告旧 `HP V1 Catalog Maintainer` 用户数量并保留可查的原分配，须人工明确授予新角色。V1-18 负责受控编辑界面。

迁移操作、审核、盘点和期初专项签核独立授权且允许人员兼任。最终签核默认准备人与签核人分开，经明确授权的例外可自审并记录授权和原因。签核独立于全局审批开关。授权主体、例外机制和状态机由后续任务设计。仓库数据范围单独校验，上传、读取、审核、冻结、签核和读取文件均须服务端验证所涉范围与当前能力。V1-15 私有导出基础可供复用，安全上传、期初审核和跨仓文件授权待实现和验收。迁移相关搜索、文件与导出延续 V1-15 的产品技术字段隔离和撤权重验。

员工读取历史标识及其筛选结果需要 PRODUCT_READ。库存 Excel 继续按实际技术列与搜索授权记录重验，历史标识随既有规格列或 SKU 标识列投影。站点操作员仍通过 Bench 管理受限升级处置及原生诊断。

## V1-16B 迁移能力

Migration Operate、Migration Review 和 Migration Execute 独立授予，均须同时具备 Product Read。实际创建与更新按组复查 Product Maintain 或 Parameter Maintain。私有下载复查当前 Migration Operate 与 Product Read。报告生成和下载同时需要 Export。 [主数据迁移契约](V1-16B-MASTER-DATA-MIGRATION.md)
