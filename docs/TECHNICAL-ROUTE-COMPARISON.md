# V1 技术路线比较

2026-11-19，Asia/Shanghai。供技术选型审查。范围为 ERPNext + 自定义 Frappe App 与 Frappe-only + 自定义库存引擎。两者在同一锁定 Frappe 16.55.0 / MariaDB 11.8.9 实验环境的独立数据库验证。ERPNext 的原生结果和适配结果沿用 Stage 1B–1F 的实测；本轮未改动原型。Frappe-only 事实以 Stage 2A 报告为准。
[Stage 2A 实测报告](STAGE2A-FRAPPE-ONLY-SPIKE-REPORT.md) · [PRD](PRD.md) · [ERPNext 验收计划](ERPNext-VALIDATION-PLAN.md)

## 可比业务场景

| 场景 | ERPNext + 自定义 App | Frappe-only |
| --- | --- | --- |
| 真实批次、无批次与精确扣减 | Stage 1B 通过。API 的无批次为 `null`，原生库用按 SKU 保留的系统 Batch、Batch 分配及 Bundle。原生库存角色能看到内部键。 | Stage 2A 通过。业务表使用 SQL NULL，MariaDB 生成独立索引列，数据库拒绝重复 NULL 桶。仍需正式制定批次规范、主数据及归档规则。 |
| 余额、事务、并发与精度 | Stage 1E 通过真批次及无批次并发 10 扣 7、多行回滚、1.125 − 0.125、幂等。ERPNext 提供库存执行，适配层加公司锁、精确扣减、精度验证及业务幂等。 | Stage 2A 通过对应精度、并发、幂等和回滚用例。业务服务承担 Decimal、桶级锁、审计及对账。两种原型的插桩等待时间只证明发生争用，无法据此比较吞吐。 |
| 业务审计和纠错 | Stage 1F 通过同事务事件、插入与提交故障回滚及简单更正，保留 SLE/Bundle 和单独业务事件。后台重估样本可改 SLE 元数据，原生取消可改写历史关联。 | Stage 2A 通过审计插入故障回滚、独立事件链与逐桶重建。业务记录和库存执行事实可共用事件表，余额是其投影；数据库提交连接中断沿用 ERPNext 已有证据，Frappe-only 未重跑该故障点。 |
| 两段移库和多个部分接收 | Stage 1D/1E 通过 STD61、无批次、分次接收、并发及共享在途，复用原生累计接收、Stock Entry、SLE 和 Bundle。需固定目标和批次并隔离在途。Stage 1F 另证实未收余量能退回。 | Stage 2A 通过真批次、NULL、两次接收、幂等、完成后禁收及共享在途行级上限。自行实现发出、累计、事件腿、权限及并发。部分接收后的剩余退回未实现，已完成移库下游更正也未实现。 |
| 盘点版本 | Stage 1E 原型允许不同键的旧盘点覆盖。Stage 1F 以事件和原生流水摘要校验后通过旧任务、往返、并发和零盘盈，零盘盈用正式 Material Receipt。 | Stage 2A 以同事务桶序号校验，覆盖收发、数量往返、并发、重复提交和零盘盈。单桶试验记入一个业务 COUNT 差异。无差异任务记录完成且保留桶版本。多桶截止、晚到单据和冻结规则待设计或验证。 |
| 动态仓库授权 | Stage 1C 的专用角色与明确叶仓授权通过，另测 225 个自定义和原生入口。叠加原生库存角色会暴露数据，动态 ALL 未实现。 | Stage 2A 的单桶 API 验证 ALL 自动覆盖新仓，SELECTED 保持分配范围，NONE 拒绝。移库同时校验双方。通用 REST 探针范围比 Stage 1C 小，报表、附件、导出及后台权限仍待实现和验收。 |

## 架构、运维与后续产品

| 项目 | ERPNext + 自定义 App | Frappe-only |
| --- | --- | --- |
| 未来库存价值 | 已实测数量链仍走 ERPNext 内部估值，研究组配置无 GL。原生估值和财务接口可供未来评估，零成本历史切换、回填和关账仍需验证。 | 没有引入估值。可设计以事件 ID 关联的独立成本层，保留数量账；须自行实现成本规则、期初估值、重算、关账及可能的财务衔接。 |
| Frappe / ERPNext 升级 | 两个上游与适配 App 均需回归。重点是旧批次字段弃用、Bundle、SLE、重估、取消、原生角色和文档入口变化。 | 上游只需兼容一个框架。仍要维护自建 SQL、MariaDB 生成列、事务行为、DocType 迁移、API 鉴权与库存引擎。实验未执行跨版本升级。 |
| 阿里云 Linux、备份恢复 | 实验中两条路线共用同一 Bench 和服务栈。生产仍需 HTTPS、私有数据库及 Redis、最小权限、监控、定期备份与恢复。ERPNext 多出后台重估和两套库存事实的一致点。 | 移除 ERPNext 应用依赖。生产组件基线仍有 Frappe、MariaDB、Redis、Web 及必要的 worker，需验证备份保留生成列和约束、恢复后逐桶重建、任务及幂等边界。两条路线的云部署和恢复均未实测。 |
| 微信小程序、OCR / AI | 借助同一 Frappe 鉴权和业务 API，需将原生 DocType / 管理员密钥隔离在服务内部。 | 同样可暴露版本化业务 API，独立掌控域对象。两者均待实现小程序登录、账号绑定、授权、上传和 OCR 草稿审核，外部 AI 应先产草稿并由人工确认。 |
| 产品档案、属性和搜索 | Item/Item Group、品牌、Data Import 可以作为基础。规格与多品牌 SKU、分类属性模板、审计和受限搜索仍需定制。现有原型未通过 E11/E16。 | Frappe 提供 DocType、权限和导入基础。SKU、品牌规格、模板、历史属性、型号与别名索引、批量导入校验及业务幂等由项目设计。Stage 2A 只创建测试 SKU，E11/E16 未实现。 |
| 生产完整性 | ERPNext 原生能力可减少部分库存开发，需要为自定义审批、API、纠错、报表和权限补齐完整工作流，并隔离原生高权限、后台重估与清理。 | 少一套库存文档及内部估值边界，库存正确性与长期运维完全由项目承担。需要压测、死锁重试、月末截止、完整纠错、不可变审计信任方案、对账报表及恢复。 |

架构与部署差异是根据各自依赖和已经观察的运行行为推断。原型体积没有用于估算完整系统成本。

## 粗略工作量

范围用于排序评审，单位为熟悉 Frappe 的工程师人周。假设约 1 名主操作员、10 名查询员、1000 SKU 内、V1 只管数量，使用同一套必要的 V1 UI 和服务端 API。区间根据待交付子系统估算，未用原型行数、时长或装机内存外推，也未计入未来财务及外部客户端开发。

| 工作包 | ERPNext + 自定义 App | Frappe-only |
| --- | --- | --- |
| 共同业务能力（产品、搜索、审批、UI、导入导出和业务 API） | 7–12 | 7–12 |
| 库存内核与适配加固（批次、并发、幂等、盘点、移库、纠错） | 2–4（含双账与原生生命周期） | 3–5（含自建写入规则与全账校验） |
| 全链路权限、回归、部署/恢复演练 | 3–5（额外原生入口、后台及双账） | 2–4（自建库存约束、恢复与回放） |
| 规划区间 | 12–21 | 12–21 |

两条范围重叠，无法从本轮证据判定开发更快。以完成自动化覆盖后的单次常规升级为例，估计 Frappe-only 需 1–3 人日复核框架、存储约束与引擎，ERPNext 适配需 2–5 人日，同时复核原生角色、Bundle、估值和双账。两者都需重跑数量、权限和恢复回归。这些是待评审的维护计划量，升级和故障修复的实际时长未测。

## 推荐及条件

**在 V1 只管数量且团队承诺维护库存引擎的前提下，建议评审优先考虑 Frappe-only。** 真实 NULL、独立桶约束、单账重建、按桶并发和动态仓库权限已验证。ERPNext 的部分接收、标准单据、成熟库存与估值能力有实际复用价值。如果近期估值、财务或标准 ERP 流程进入范围，ERPNext 候选的收益将上升，仍需解决原生权限、后台作业和双账一致性。

进入生产开发之前应补齐两条路线各自的未通过和未验证验收。业务需先决定盘点冻结或版本及重盘要求、已完成移库和下游出库的更正、批次大小写、同仓不同库位的两阶段规则、期初迁移及审计信任等级。最终技术决议由项目方评审。
